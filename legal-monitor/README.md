# Legal Monitor

Ежедневный (будни, 08:50 по Уфе) сборщик двух источников — kad.arbitr.ru и
трекинг Почты России — с одной сводкой в Telegram о том, что изменилось.
Тишина по умолчанию: если новостей нет и оба источника ответили, сообщение не
отправляется.

## ⚠️ Данные не являются процессуально достоверными

Это вспомогательный инструмент оповещения, а не источник истины. Даты,
которые он показывает (вручение, сроки ответа на претензию, дата заседания),
**всегда перепроверяются вручную по первоисточнику** (карточка дела на
kad.arbitr.ru, официальный трек Почты России) прежде чем на них полагаются
для расчёта процессуальных сроков. Сайт kad.arbitr.ru целенаправленно
противодействует автоматическому доступу и может в любой момент поменять
защиту — код в этом случае должен сообщить о сбое в Telegram, а не молчать.
Если сайт начнёт показывать капчу — это сигнал сообщить заказчику, а не
пытаться её обойти; такой обход в этом проекте намеренно не реализован.

## Статус на 2026-08-14 — что проверено вживую, а что нет

Собиралось в песочнице без доступа к реальным cookies kad.arbitr.ru и без
реальных учётных данных Почты России. Ниже — честный отчёт по каждому слою,
без которого нельзя доверять системе вслепую.

| Слой | Статус |
|---|---|
| `core` (SQLite-схема, диффер, реестр, оркестратор) | ✅ Полностью протестировано локально (`pytest`), включая идемпотентность повторного прогона и дедупликацию задним числом опубликованных событий. |
| `notifier` (форматирование, экранирование, разбиение на сообщения, срок ответа на претензию) | ✅ Полностью протестировано локально. |
| `pochta_client` (SOAP) | 🟡 **Частично подтверждено вживую**: реальный вызов `getOperationHistory` на `https://tracking.pochta.ru/rtm34` с плейсхолдер-логином/паролем дошёл до сервера и получил осмысленный SOAP fault "Ошибка авторизации" — то есть WSDL, имя метода и структура запроса (`OperationHistoryRequest` + `AuthorizationHeader`) подтверждены боевым сервером. Не проверено: разбор реального успешного ответа и классификация статусов (нет реальных `POCHTA_LOGIN`/`POCHTA_PASSWORD` и реального трек-номера). |
| `kad_client` — поиск (`SearchInstances`) | 🟡 Частично подтверждено: запрос без cookies реально возвращает `HTTP 451` от `ddos-guard`, как и описано в ТЗ — логика ретрая на 451 писалась под реальное поведение сайта. **Не подтверждён формат успешного ответа.** В ТЗ он описан как HTML; по независимым данным этот эндпоинт исторически отдаёт JSON. Ни то, ни другое не удалось проверить вживую (нет валидных cookies — см. ниже), поэтому парсер распознаёт оба формата по факту и громко падает (`KadResponseFormatUnknown`), если не подходит ни один. **Первое, что нужно сделать на реальном сервере — заменить синтетические фикстуры в `tests/fixtures/` на реальный сохранённый ответ.** |
| `kad_client` — карточка дела (события, заседания) | 🔴 **Разведка не проведена.** ТЗ требует найти реальный внутренний эндпоинт карточки, запустив headful Playwright против реального дела — это не удалось сделать здесь (см. ниже). Реализован только описанный в ТЗ fallback: полный рендер карточки через Playwright и разбор DOM с CSS-селекторами, подобранными по общим ожиданиям от вёрстки KAD, но не проверенными на реальной странице. Это самый ненадёжный участок системы — см. `docs/kad-endpoints.md`. |
| `cookie_service` (Playwright, обход WASM-челленджа) | 🔴 **Не проверен вживую.** Внутри песочницы, где это писалось, TLS-хендшейк Chromium к любому HTTPS-хосту сбрасывается исходящим MITM-прокси песочницы сразу после ClientHello (подтверждено через `chrome --log-net-log`: `SOCKET_READ_ERROR net_error=-101/ECONNRESET`), при этом `curl`/`httpx` через тот же прокси работают нормально — то есть это несовместимость конкретно Chromium с прокси песочницы, а не блокировка со стороны kad.arbitr.ru. На обычном сервере заказчика такого перехватывающего прокси нет, и весь проект построен на допущении, что там этот шаг сработает. **Это первое, что нужно проверить на реальном сервере**, прежде чем доверять чему-либо ещё. |

Подробности и точные команды для каждого пункта — в `docs/kad-endpoints.md`.

### Порядок первого запуска на реальном сервере

1. `cp .env.example .env`, заполнить реальными значениями.
2. `docker compose build`.
3. `docker compose run --rm monitor python -m legal_monitor.cookie_service --force` — убедиться, что `pr_fp` и `wasm` реально приходят. Если нет — дальше двигаться бессмысленно.
4. Сделать один реальный поиск (`kad_client.search`), сохранить сырой ответ в `tests/fixtures/`, поправить `parser.py`, если формат отличается от того, что он ожидает.
5. Провести разведку карточки дела (headful Playwright на реальном деле) и задокументировать найденный эндпоинт в `docs/kad-endpoints.md`, как описано там.
6. Проверить `pochta_client` с реальными `POCHTA_LOGIN`/`POCHTA_PASSWORD` и реальным трек-номером; свериться, что классификация статусов (вручено/неудачная попытка/возврат/прибытие в место вручения) соответствует реальным `OperType`/`OperAttr`.
7. Добавить реальные дела и отправления через CLI, прогнать `run --dry-run`, свериться с сообщением глазами.
8. Настроить `cron/legal-monitor.cron` под таймзону сервера.

## Архитектура

```
legal-monitor/
├── legal_monitor/
│   ├── cookie_service/   # Playwright: добывает и кэширует cookies КАД
│   ├── kad_client/       # httpx + Playwright fallback: поиск дел, карточки
│   ├── pochta_client/    # SOAP (zeep): трекинг Почты России
│   ├── core/             # SQLite-реестр, диффер, оркестратор
│   ├── notifier/         # Telegram
│   ├── config.py
│   └── __main__.py       # CLI
├── docs/kad-endpoints.md
├── tests/
├── docker-compose.yml
└── Dockerfile
```

Каждый модуль можно запустить отдельно для отладки, например:

```
python -m legal_monitor.cookie_service --force
python -m legal_monitor.kad_client.card <case_guid>
```

## Почему sqlite3, а не SQLAlchemy

Одна встроенная SQLite-база, разворачивается `docker compose up` без внешних
зависимостей. Схема небольшая и стабильная (7 таблиц), ORM здесь добавила бы
слой абстракции без реальной выгоды — заказчик сам администрирует сервер и
умеет читать SQL напрямую. `sqlite3` — часть стандартной библиотеки, это
минус одна зависимость.

## Конфигурация

Скопировать `.env.example` в `.env` и заполнить:

| Переменная | Назначение |
|---|---|
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | куда слать сводку |
| `POCHTA_LOGIN`, `POCHTA_PASSWORD` | единичный доступ на tracking.pochta.ru (бесплатно, 100 запросов/сутки) |
| `KAD_USER_AGENT` | должен совпадать с UA, который использует `cookie_service` в Playwright-контексте — иначе cookies не примутся |
| `DB_PATH` | путь к SQLite-файлу |
| `LOG_LEVEL` | уровень логирования |
| `DEFAULT_CLAIM_RESPONSE_DAYS` | срок ответа на претензию по умолчанию (можно переопределить на конкретную претензию через `--response-days` в `add-parcel`) |
| `COOKIES_CACHE_PATH` | путь к кэшу cookies |

`.env`, `data/`, `*.db`, `cookies_cache.json` — в `.gitignore`, в репозиторий не попадают.

## CLI

```
python -m legal_monitor add-case А07-12345/2025 --counterparty "ООО Ромашка" --role plaintiff
python -m legal_monitor add-parcel 80082806838014 --claim "Претензия №15 от 12.08.2026" --counterparty "ООО Ромашка"
python -m legal_monitor list --active
python -m legal_monitor run --once        # обычный прогон, шлёт в Telegram при наличии новостей
python -m legal_monitor run --once --dry-run   # печатает сводку в консоль вместо отправки
```

`--role` принимает `plaintiff` / `defendant` / `third_party`. Добавление дела
и отправления идемпотентно — повторный вызов с тем же номером/треком просто
скажет «уже отслеживается».

## Docker + cron

```
docker compose build
docker compose run --rm monitor add-case ...
docker compose run --rm monitor run --once
```

Пример строки cron — в `cron/legal-monitor.cron` (08:50 по Уфе = 03:50 UTC,
если сервер живёт в UTC — проверить `timedatectl`). Только будни: по выходным
суды не заседают и почта не вручает.

## Тесты

```
pip install -r requirements-dev.txt
pytest
```

Покрыты офлайн (без сети): диффер и идемпотентность реестра
(`test_differ.py`, `test_registry.py`, `test_orchestrator.py`), парсер
HTML/JSON-ответов КАД на синтетических фикстурах (`test_parser.py`,
см. предупреждение в заголовке фикстур — это не настоящий захваченный ответ),
форматирование и разбиение Telegram-сообщений (`test_formatter.py`).
`cookie_service`, реальный сетевой слой `kad_client`/`pochta_client` тестами
не покрыты — их можно проверить только вживую, см. таблицу статусов выше.

## Принципы (из ТЗ)

- Один цикл в сутки, КАД опрашивается пачкой (`CaseNumbers` — один POST на
  всех отслеживаемых дел), никаких параллельных ретраев.
- Отказ одного источника не роняет второй — см. `core/orchestrator.py`,
  `_run_kad_leg`/`_run_pochta_leg` изолированы друг от друга.
- Новизна события определяется хешем содержимого (`core/differ.py`), а не
  временем последней проверки — события на КАД публикуются задним числом.
- Молчаливые падения недопустимы: любой сбой источника явно показывается в
  Telegram-сводке (`⚠️ КАД не ответил (...)`), а не проглатывается.
